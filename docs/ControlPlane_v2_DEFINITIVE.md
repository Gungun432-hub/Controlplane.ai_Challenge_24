# PART 1 — What the third review adds that I had not said

It agrees with my diagnosis, which is reassuring but not useful on its own.
Five things in it are genuinely better than what I wrote, and one is wrong.

## ✅ 1. The thread-cancellation nuance — and it goes further than they took it

> *"Python threads cannot be reliably killed once already running. The fix should
> not pretend that `future.cancel()` stops a running detector."*

Correct, and I under-specified this. But the consequence is bigger than they
state, and it is worth working all the way through:

```python
_POOL = ThreadPoolExecutor(max_workers=8)     # ← ONE pool, eight slots
```

If a slow detector blows the deadline, we stop *waiting* for it — but it keeps
running and keeps holding a slot. Under sustained load, timed-out work
accumulates in the same pool that inline work needs. **The pool saturates, and
the latency budget you just "enforced" becomes unenforceable again**, because new
requests queue for a thread before they can even start.

So the fix is not one line. It is:

```
_INLINE_POOL   = ThreadPoolExecutor(max_workers=8)    # request path only
_DEFERRED_POOL = ThreadPoolExecutor(max_workers=4)    # timed-out + async work
_DEFERRED_Q    = BoundedQueue(maxsize=N)              # explicit capacity
```

with a rule: **a detector that misses the deadline is abandoned by the request,
and its continuation is not allowed to re-enter the inline pool.** In this
design the inline pool's occupancy is bounded by concurrency, not by the
slowest detector.

**This is worth saying in the room**, because it is the difference between
someone who read about timeouts and someone who has implemented one:

> "Stopping the wait is easy. The hard part is that the abandoned work is still
> running, so if it shares a pool with the request path your budget stops being
> enforceable under load. We separated the pools."

## ✅ 2. A far richer detector status enum

Mine had four states. Theirs has eight, and each earns its place:

```
completed · timed_out · failed · not_configured
skipped_by_policy · queued_async · completed_async · stale
```

`skipped_by_policy` and `not_configured` matter because they are *legitimately*
absent, and conflating them with `failed` would produce false alarm fatigue in
exactly the population you least want to annoy — compliance people.

## ✅ 3. The governance-status decision matrix

I gestured at "policy decides"; they wrote the table. Adopt it, and make it
**YAML-driven** rather than hardcoded, so it is policy rather than code:

| Situation | read / draft | advise / decide | execute |
|---|---|---|---|
| advisory detector timed out | release, marked | escalate if relevant | approval or block |
| **mandatory** detector timed out | escalate | block or escalate | **fail closed** |
| advisory detector failed | release, marked | escalate if policy says | approval |
| capability check unavailable | **do not execute** | escalate | **block** |

## ✅ 4. Deferred-queue saturation must be visible, never silent

> *"Do not silently drop tasks; record queue saturation; mark governance
> degraded; apply backpressure; expose deferred backlog."*

Right — and see my Idea 1 below, which turns this from an ops concern into one

## ✅ 5. Defect-targeted acceptance tests

This is the most practically valuable section in their document. Not "test the
system" but *test the exact bug*:

```
slow inline detector      → response returns at ~the deadline, not after it
timed-out detector        → contributes no score, and is not read as "clean"
async detector            → does not delay evaluate() return at all
mandatory detector fails  → cannot permit an irreversible execution
declared=draft + execute-capable tool → effective becomes execute
expired control           → no longer affects policy resolution
```

Six tests. Write them **before** the fixes. They are also your best possible
answer to "how do you know it works?" — you point at the test that fails on the
old code and passes on the new.

## ❌ Where it is wrong — the LLM recommendation agent

It proposes a Recommendation Agent that "may use an LLM to summarise why an
application became risky, cluster issues, suggest remediation."

In a **governance** product this is a trap. The first question a serious judge
asks is: *"so your governance advice is generated by the same class of system
you exist to police?"* You do not have a good answer to that.

**My rule: recommendations are derived deterministically and cited numerically.
A model may phrase one; it may never derive one.**

```
rule_id:      COST.DUPLICATE_PROMPTS
evidence:     {duplicate_share: 0.68, cache_hit_rate: 0.32, spend_inr: 18400}
derivation:   deterministic
text:         "68% of this system's prompts are near-duplicates. Enabling the
               embedding cache would cut roughly ₹6,100/month."
```

Every recommendation carries its rule id and its numbers. That is checkable.
"The LLM thought so" is not.

## ⚖️ Where I partly disagree — "no live add-a-detector gimmick"

They are right that theatrics undercut a rigour-first pitch, and after you have
just told the room you found and fixed your own latency bug, a party trick jars.

But the *claim* is still one of your strongest. **Reframe it from stunt to
evidence:** show the four-line diff and the test that proves a new detector
requires no change to any existing file. Offer the live add once, in one
sentence, and move on whether or not anyone takes it.

# PART 2 — Four ideas none of the three reviews raised

## 💡 Idea 1 — Governance lag as a first-class fleet metric

Once deferred verification is real, a new quantity exists that has never existed
in your system: **the gap between decisions made and decisions fully verified.**

```
Governance lag
  4,217 decisions awaiting deferred verification
  oldest: 38 minutes
  affected systems: marketing-copilot (3,901), order-desk (316)
  status: GOVERNANCE DEGRADED — verification is behind production
```

Every competitor reports whether an answer was safe. **None of them report
whether the organisation's governance is currently keeping up with its own AI.**

This falls straight out of doing the async fix properly, which is the point: a
correctness fix becomes a differentiating feature. And it gives the Resource
Governor a third thing to fight for — verification capacity — alongside money
and reviewer minutes.

## 💡 Idea 2 — Shadow mode, and it is a sales mechanism, not a feature

All three reviews propose policy simulation: replay the ledger under a candidate
policy. Correct. But that is an *internal* tool. Turn the same machinery
outward:

> **"Point ControlPlane at your last 1,000 production AI responses. We run in
> shadow mode — we change nothing, block nothing, and cost you no integration.
> At the end we hand you a report: here is what we would have caught, here is
> what it would have cost, here is how much human review you would have needed."**

This is the answer to Sir's hardest question — *who buys it and why* — because
it removes the buyer's risk entirely. Nobody has to trust your thresholds. They
find out on their own traffic, with no code change and nothing in the request
path.

It also costs you almost nothing to build: it is `evaluate()` with the router's
action discarded and the record kept. Your `force_offline` flag already proves
the pattern exists.

**And it is a fantastic demo beat**, because you can run it live: *"this is a
thousand answers from a system that has never been governed. Here is what we
found in eleven seconds."*

## 💡 Idea 3 — Governance completeness as a contractual number

Once every response carries `fully_governed` / `partially_governed` /
`ungoverned_*`, a number exists that an enterprise could put in a contract:

```
finance-decision-assistant     governance completeness  99.2%   (7d)
marketing-copilot              governance completeness  86.4%   ← degraded
```

That is an SLA. No governance product currently offers one, because none of them
distinguish "we checked and it was fine" from "we released it without
checking." You can, and it is a direct consequence of the detector-status fix.

> "Every product in this space tells you whether the answer was safe. We also
> tell you what fraction of your decisions were actually fully governed — and
> we'll put a number on it."

## 💡 Idea 4 — Two clocks, reported separately

Right now `added_latency_ms` conflates two genuinely different things. Separate
them permanently:

```
decision latency        48 ms     what the user waited for
verification latency   2.3 s      when the record became complete
```

This makes the async architecture legible instead of suspicious, it is honest
about what your published p50 measures, and on the ledger entry it renders as a
lovely small visual: *decision at t=48 ms · record sealed at t=2.3 s*.

It also kills a hostile question before it is asked: *"so is your 48 ms real or
did you just move work out of the measurement?"* — **Both numbers are on
screen. That is the answer.**

# PART 3 — The final architecture

## 3.1 Layers

```
┌── DATA PLANE · per request · bounded · deterministic ─────────────┐
│ identity → effective capability → resolved policy snapshot        │
│ → provider → inline detectors (deadline-enforced) → risk price    │
│ → pass/repair/escalate/block → evidence                           │
│ ONE authoritative router. The fleet layer never competes with it. │
└────────────────────────────┬──────────────────────────────────────┘
                             │ evidence
                 ┌───────────▼───────────┐
                 │  APPEND-ONLY LEDGER   │  decisions AND control decisions
                 └───────────┬───────────┘
                             │
┌── CONTROL PLANE · per system · asynchronous ──────────────────────┐
│ projections → monitors → governors (recommend) → SUPERVISOR       │
│ (deterministic arbitration) → scoped expiring controls            │
│ → effectiveness measurement                                        │
└────────────────────────────┬──────────────────────────────────────┘
                             │ versioned control snapshot
┌── IMPROVEMENT · per policy ───────────────────────────────────────┐
│ human verdicts → bounded calibration                              │
│ ledger replay → policy simulation · regression detection          │
│ shadow mode → prospect onboarding                                 │
└────────────────────────────────────────────────────────────────────┘
```

## 3.2 Agents, and the honest boundary

```
AGENTS        Supervisor (deterministic authority)
              Safety Governor · Resource Governor · Assurance Governor

EVIDENCE      Detectors — per response  (grounding, uncertainty, privacy,
PRODUCERS                                fairness, cost)
              Monitors  — over time     (exposure, budget, queue, latency,
                                         detector health, governance lag)
```

**Four agents, not sixteen.** A component that produces evidence and cannot be
told "no" is a detector, not an agent — and calling it one is the exact tell a
technical judge looks for.

The governing sentence, which I am adopting from the third review because it is
better phrased than mine:

> **Agents analyse and recommend. Deterministic policy code arbitrates. Humans
> approve irreversible fleet actions.**

**This is still strongly agentic**, and here is why it survives the hostile
question: the agents hold persistent state, pursue objectives that genuinely
conflict, can be refused, and can be overruled. The Resource Governor vetoes the
Safety Governor's request for more compute; something must referee; the referee
is deterministic and its reasoning is signed. You cannot write that as a
pipeline.

**Resource Governor manages three currencies:** rupees, reviewer-minutes, and
verification capacity. Everyone manages the first. Your own research says the
second is 94.8% of what oversight actually costs. The third did not exist until
you fixed the async path.

## 3.3 Arbitration — four rules, strict precedence, no model in the loop

```
RULE 1 · HARD GATES ARE NOT TRADEABLE
  Unauthorised execution · confirmed PII leakage · missing mandatory approval ·
  contradiction of the source of record · a mandatory detector that did not
  complete on an irreversible action. None of these is exchangeable for lower
  cost or lower latency. Ever.

RULE 2 · REVERSIBILITY DOMINATES
  On irreversible actions — by EFFECTIVE capability, never declared — Safety and
  Assurance outrank Resource. Always.

RULE 3 · BELOW THAT LINE, PRICE THE TRADE
  Δ(exposure) × blast_radius   vs   Δ(₹) + Δ(reviewer-min) + Δ(verification)
  Both sides in units already computed. Arithmetic, not opinion.

RULE 4 · DEGRADE TOWARDS EVIDENCE, NEVER TOWARDS SILENCE
  Record the unmet constraint, lower the governance status, show it on screen,
  take the safest permitted action. A governance system under pressure must
  fail loudly.
```

Rule 2 is **your blast-radius idea promoted from scoring one response to
governing the whole plane** — it stops being a heuristic inside a function and
becomes the constitution of the system.

Every arbitration is ledgered, with the requests, the evidence, the rule
applied, the winner, and what stayed unmet.

> "We audit the AI. We also audit the thing that audits the AI. Ours is the only
> one of the two that anybody can currently ask questions of."

# PART 4 — The execution contract

## 4.1 Detector result

```python
DetectorResult(
    name="grounding", score=0.82, confidence=0.91,
    status="completed",          # 8-state enum, Part 1 §2
    ran_inline=True,
    started_at=..., completed_at=..., latency_ms=41.2,
    queue_delay_ms=0.0,          # deferred work only
    evidence_refs=[...], error_code=None,
)
```

**A failure must never be representable as `score=0`.** That is
indistinguishable from a clean check, and on a privacy detector it is the worst
possible confusion in the system.

## 4.2 Request path

```python
done, pending = wait(inline_futures, timeout=budget_s)   # deadline ENFORCED
results  = [f.result() for f in done]
results += [DetectorResult(n, score=None, status="timed_out") for n in pending]

gov = governance_status(results, policy, effective_action)   # YAML-driven table
decision = route(answer, results, price(results...), policy, effective_action)
emit_evidence(...)
return decision                                          # ← returns HERE

# abandoned + async work → DEFERRED pool, bounded queue,
# amends the ledger, never touches the returned response
```

Three invariants, each a testable statement:

1. **The deadline is a guarantee**, not a measurement.
2. **Deferred work amends evidence and future governance. It never mutates a
   returned response.**
3. **Absence is explicit.** A check that did not happen is recorded as not
   having happened.

# PART 5 — Capability: the most important single change

Blast radius is the load-bearing idea of the entire product. If its input can be
forged by the caller, the idea is decorative. This is the change that fixes
that, and it is the one I would protect above everything else on this list.

```yaml
- system_id: it-ops-agent
  owner: Priya Nair
  department: Platform Engineering
  environment: production
  policy_profile: decision_support
  jurisdiction: in
  budget_inr_month: 20000
  review_minutes_week: 180
  allowed_capabilities: [read, draft, advise]
  allowed_tools:
    - name: restart_service
      effective_action: execute
      reversible: false
      approval_required: true
      allowed_environments: [staging]      # NOT production
    - name: summarise_incident
      effective_action: draft
      reversible: true
```

```python
def resolve_capability(req, registry) -> Capability:
    system = registry.get(req.system_id)            # unknown → strictest default
    tool   = system.tool(req.tool_name) if req.tool_name else None
    if tool is None:
        effective = min_rank(req.declared_action_class, system.max_capability)
    else:
        effective = tool.effective_action            # the binding, not the claim
        if tool.max_amount_inr and req.amount > tool.max_amount_inr:
            effective, approval = "execute", True
        if req.environment not in tool.allowed_environments:
            return Capability.denied("tool not permitted in this environment")
    mismatch = RANK[req.declared_action_class] < RANK[effective]
    return Capability(effective, tool.reversible, approval, mismatch)
```

The ledger records **`declared_action_class`**, **`effective_action_class`** and
**`capability_mismatch`**. A mismatch is itself a safety event that moves the
system's health state.

Unregistered `system_id` → governed under the strictest profile and shown as
`unregistered`. That is your honest, minimal answer to the shadow-AI problem
all three competitors headline: **you notice; you do not claim to discover.**

# PART 6 — Controls

Never mutate a base policy. Compose:

```
base profile + jurisdiction overlay + approved control overlay
                                   = resolved snapshot (versioned)
```

which is **exactly the mechanism your EU and India overlays already implement**.
One mechanism, three sources, fully reconstructible from the ledger.

Every control carries: `control_id` · `system_id` · `type` · `scope`
(action classes, tools) · `reason` · `evidence_refs` · `requested_by` ·
`rule_applied` · `approved_by` · `policy_version` · `starts_at` ·
**`expires_at`** · **`rollback_control`** · `expected_effect` ·
`observed_effect` · `status`.

| Tier | Controls |
|---|---|
| **Autonomous** | `REQUIRE_HUMAN` · `TIGHTEN_POLICY` · `PROMOTE_DETECTOR_INLINE` · `RESTRICT_TOOL` · `ADD_CITATION_REQUIREMENT` · `REDACT_OUTPUT` · `ENABLE_CACHING` · `LOWER_CONTEXT_LIMIT` · `ROUTE_LOW_RISK_CHEAPER` |
| **Guarded** | `THROTTLE` · `DOWNGRADE_MODEL` · `FREEZE_NEW_SESSIONS` |
| **Human-approved** | `SUSPEND` · `QUARANTINE` · `RELAX_SAFETY_BOUNDARY` |

**Why suspension stays human:** an autonomous agent that can unilaterally halt a
production system is a worse risk than the one it prevents — which is the
identical argument your own `router.py` docstring already makes about rationing
BLOCK. Applying one principle consistently at two scales is what an experienced
judge notices.

**Closed loop.** Every control declares an expected effect and a measurement
window; the effectiveness evaluator compares and the control is retained,
expired or rolled back. Label it **observed before/after**, not causal proof —
you have no control group, and saying so is a credibility gain.

# PART 7 — Fleet state and health

**Exposure** = `Σ risk_price`, plus per-100-requests so volume cannot mask
consequence.

> "`order-desk` logged forty findings this week. `finance-assistant` logged
> three. `finance-assistant` is red — its three were payment executions,
> `order-desk`'s forty were reads. We don't count incidents. We price
> consequence."

**Per system:** exposure (total, intensity, by action class, trend) ·
`capability_mismatch` count · hard-gate trips · route mix · **governance
completeness %** · ₹ spend vs budget · reviewer-minutes vs budget ·
verification backlog · queue depth and oldest age · detector health · active
controls · `unregistered`.

**Health is a state, not a colour**, and each state is a contract:

| State | What the system may do |
|---|---|
| `healthy` | normal traffic, all configured tools |
| `warning` | normal traffic, owner notified |
| `guarded` | tighter thresholds, expensive detectors promoted inline |
| `approval_required` | irreversible actions queue for a human |
| `tool_restricted` | text continues; risky tools disabled |
| `throttled` | rate limited, explicit retry |
| `degraded` | approved fallback model / reduced context |
| `suspended` | new production traffic refused (human-approved only) |
| `recovering` | controls remain until improvement is measured |

**Review triage** by `expected consequence ÷ estimated review effort`, not FIFO.
When attention runs short: reserve humans for irreversible actions, let
reversible drafts proceed with deferred review, and mark the organisation
**attention-constrained** on screen.

# PART 11 — What we deliberately do not build

- **No LLM in enforcement, and none in deriving recommendations.** A model may
  phrase; it may never derive. Judgement is used exactly where it is genuinely
  needed — the rationed judge above risk price 60, capped at 90 calls/1,000.
- **No autonomous suspension.**
- **No shadow-AI network discovery.** We flag unregistered traffic.
- **No database, no multi-tenancy, no auth.** JSONL keeps evidence readable with
  ordinary tools; at volume it becomes a real store and we say so.
- **No causal claims** about control effectiveness — observed before/after.
- **No second router.** The fleet layer changes the *inputs* to the existing
  engine. There is exactly one authoritative decision path.
- **The ledger is "tamper-evident under protected key management."** Hash
  chaining detects tampering and ordering breaks; HMAC authenticates holders of
  the shared secret; independent non-repudiation would need asymmetric signing.
  Never "tamper-proof."

## The thesis

> ControlPlane is a consequence-aware operating layer for enterprise AI with two
> enforcement tiers. A deterministic per-response gate prices every answer by
> what it is about to **do** — derived from the tool it can actually call, never
> from what the caller claims — and routes it to pass, repair, escalate or block
> under a deadline it genuinely enforces, recording not just whether the answer
> was safe but whether the checking was complete. Above it, a control plane
> watches every AI system's exposure, spend, reviewer burden and governance
> completeness, and applies scoped, expiring, reversible controls when a system
> drifts. Three governor agents pursue genuinely competing objectives; a
> deterministic supervisor arbitrates on reversibility; humans retain authority
> over irreversible actions. Every decision — the AI's and the control plane's
> own — is replayable evidence. So when a system turns red you can ask it why,
> what it did about it, and whether that worked.
